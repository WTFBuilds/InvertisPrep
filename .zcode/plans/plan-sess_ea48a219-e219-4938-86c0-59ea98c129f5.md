## Backend Performance Optimization — Final Plan

### Decisions locked in
- **Goal:** fix per-request latency (2–5s responses), not concurrency.
- **Deployment:** one long-lived Render instance (free tier, kept warm by ping bots) → **per-instance in-memory cache is correct**; no Redis, no load balancer, no multi-instance work.
- No API shape changes, no client changes, no watermark appearance changes.

### Root causes (verified in code) → targeted fixes

**1. PDF pipeline — the biggest single-request cost** (`server/src/controllers/pdfController.js`)
Every view/download re-downloads the full PDF from Cloudinary (`axios.get`) + synchronously re-watermarks every page with pdf-lib (per-char `drawText`) + re-saves, with `Cache-Control: no-store`. On a 0.1 CPU free instance this is exactly your 2–5s, and it blocks the event loop.
→ Add a small **in-memory LRU cache of finished watermarked PDFs** keyed by `paperId + userId` (e.g. 40 entries, ~10 min TTL). Repeat view/download skips Cloudinary + pdf-lib entirely. Watermark stays per-user → no leakage. Set response `Cache-Control: private, max-age=600`. Import a tiny LRU util (no new deps needed — a Map-based LRU is fine, or add `lru-cache`).

**2. No gzip** (`server/src/server.js`)
→ Add `compression` middleware (new dependency). Big win on JSON list payloads over the wire. Also `app.disable('x-powered-by')`.

**3. Wasted populates on every PYQ list** (`server/src/controllers/pyqController.js`)
`PYQPaper.departmentId/branchId/sessionId` are **string slugs**, not Mongo `_id`s, so `.populate('departmentId'|'branchId'|'sessionId')` returns `null` per row while still costing 3 extra DB round-trips per request. UI already treats them as strings (renders "N/A" for branch/session).
→ Remove those 3 populates from `getPYQs`, `getAllPYQs`, `updatePYQ`, `verifyPYQ`, and `pdfController.loadPaper`. **Keep `.populate('uploadedBy')`** (a real ObjectId the UI uses for names/avatars). Add `.lean()` to read-only list queries (`getPYQs`, `getAllPYQs`, `getReports`, admin lists).

**4. Unindexed hot queries** → add `schema.index()` (auto-created, no migration script needed)
- `PYQPaper`: `{ uploadedBy: 1, createdAt: -1 }` (daily-upload-limit counts on `/pyq/upload`), `{ uploadedBy: 1, verified: 1, isActive: 1 }` (profile "my uploads").
- `Report`: `{ createdAt: -1 }` (admin reports sort).
- `Bug`: `{ createdAt: -1 }` (admin bugs sort).
- `Event`: `{ createdAt: -1 }` (events sort).
- `User`: `{ points: -1, isActive: 1 }` (all-time leaderboard).
Existing compound indexes already cover the main `/pyq?departmentId=` listing — nothing needed there.

**5. In-memory cache for static-ish public lists** (new `server/src/utils/cache.js` — small Map + TTL, single process)
- Cache public GET endpoints: `getDepartments` (TTL 60s), `getSessions` (60s), `getBranchesByDepartment` (30s), `getEvents` (30s), `getSponsors` (30s), `getPYQs` (TTL 2s — `/pyq?departmentId=` listing), leaderboard all-time (30s).
- Never cache when the query has `search`/`subjectCode` (regex-varying) and skip when an `Authorization` header is present on auth-optional list endpoints. On write endpoints (upload/verify/delete/update), invalidate the related PYQ cache key.

**6. Heavy admin endpoints**
- `reportController.getReports`: add `.limit(100)` + `.lean()` (it's currently unbounded with a 7-query nested populate).
- `eventController.getEvents`: remove the per-request `Event.countDocuments()` seed-check (currently runs on **every** request); seed once per process behind a `let`.

**7. Auth middleware** (`server/src/middleware/auth.js`)
`authenticateJWT` does a `User.findById(...)` on **every** authenticated request; `authController.getCurrentUser` then does a **second** lookup.
→ Add a 5-second in-memory cache keyed by user id for the `{role, isActive, name, email, picture}` snapshot (still propagates role/ban changes within seconds). `getCurrentUser` reuses `req.user` when present instead of re-querying.

### Explicitly out of scope
- No Redis / load balancer / multi-instance work (per your decisions).
- No watermark redesign, no API response shape changes, no client changes, no rate-limit/CORS/security changes.
- No serverless conversion.
